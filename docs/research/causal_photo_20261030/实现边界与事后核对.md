# 本轮实现边界（不修改冻结程序或已运行输出）

六次运行的事前载荷保持原SHA，以下在结果复核前由实际代码核对得出，不能伪装成预先已控制的条件。

1. JPEG环在每个时刻处理完毕后最多6帧／1秒。程序先读入新JPEG再清掉过期帧，因此读取新帧的瞬间可同时持有第7帧；`ring_peak_compressed_bytes`记录的是清理后六帧负载。复核另据逐时刻实际帧序与文件大小重算瞬间七帧负载，不能把后者隐藏。
2. 后台请求通过multiprocessing队列携带选中JPEG字节，队列及异步feeder会额外持有引用／pickle副本，后台解码亦有RGB工作区；六帧负载不是总内存。父进程`VmHWM`是整个顺序运行的累计高水位，不能据其分别推导每种策略新增内存。
3. 所有392个高分JPEG在计时外做完整性校验，因而此前已经读过文件；正式周期内仍逐帧执行`read_bytes()`并计时。系统页缓存和前序运行状态可能影响读时，未做冷缓存或隔离I/O实验；不能把观测差异全部归因于SD速度。新规则只用按时可用的几何记录和当前／过去的候选，未使用这次完整性检查得到的未来像素进行选择。
4. 预计4组各10任务的“40次”在全部实际计数完成前只是预期。实际二轮当帧组只触发9次，所有后台合计39次；二轮前台独占也只计9次。完整实机缓存的10事件、当前六次9／10和人工总数12分别保留，不把模型或轨迹编号当身份真值，也不补造相同负载。
5. 每次结束后保存raw、轨迹、照片与日志，随后才开始下一次。顺序反转的两轮有助于呈现波动，但不保证系统缓存、温度和内存状态完全相同；本阶段没有测功耗，也不是多会话独立测试。
