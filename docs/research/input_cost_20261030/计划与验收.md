# 高分JPEG读取与拷贝：拆开资源成本

2026年10月30日。上一轮是实质进展：六次真实回放定位46–48ms逐帧JPEG读取、后台饥饿和入口缺帧，否决当前因果环组合。整体目标未完成，本阶段先查清成本，不改变模型、计数、图库或拒识门限。

1. 先运行检查真实周期记录的红色命令，保留5FPS目标未达到的事实。它使用已冻结实机记录，不能由新的较窄微基准代替完整回放通过。
2. 冻结16个均匀来源帧：392时隙中的索引0,26,…,390。高分JPEG与192输入均使用已有同源回放，实际模型仍mosaic050_seed26、O8。三类假设在测量前列出：文件页缓存／存储读取、分配与复制、计算负载／内存状态交互。无相机或真实RF输入。
3. 先作独立读取，再在真实O8前向后读取，分别比较Path.read_bytes和预分配buffer的readinto。每种分别请求文件级DONTNEED与先预读，明确冷缓存请求不是实际存储访问证明；记录/proc/self/io的实际read_bytes、CPU／墙钟和minor/major faults。
4. 两次反转方法顺序，每来源每模式4条件，共2×16×4=128条独立读取和128条真实O8后读取；后者128前向，8个实际视频准入和2次预热另计。每条JPEG按原SHA校验，所有完整raw与既有同模型实机输出逐字节匹配。128条件重复同16图，不是128独立会话。
5. 禁止全局drop_caches、swapoff、修改网络／服务／固件。文件级fadvise只作用本轮16个已授权回放JPEG，在板端原任务全部结束且独占锁可用后进行。预分配最大一个JPEG缓冲；不预加载全部260MB高分图像以掩盖内存成本。
6. 全部时序、CPU、实际存储字节和内存口径都报告。微基准尚无跟踪、计数、身份并发或真实流，若不能重现原46ms也应如实保留，不能据此宣布完整系统修复或因果策略采用。
7. 输出Markdown、完整JSON与自审；核对原固件、父进程终态及服务。按证据决定是否进入输入流水线实现；不按性能最好的一组事后更改当前生产默认。
