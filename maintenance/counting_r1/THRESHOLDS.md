# R1阈值与评价合同

维护入口为`maintenance.counting_r1.tracker.SecondStageIoUTracker`。它继承仓库中冻结的NumPy ByteTrack，复用2026-10-28历史修复，唯一算法改动是在低分第二次关联中移除score融合。AST检查覆盖整个方法及其余继承规则。历史入口和板上安装未替换。

| 层 | 当前合同 | R1处理 |
|---|---|---|
| 解码候选保留 | confidence >= 0.2 | 保留；0.1–0.2在此被过滤 |
| 高分检测 | confidence >= 0.25 | 保留 |
| 低分检测 | confidence > 0.1且<0.25 | 保留；考虑解码后实际区间为[0.2,0.25) |
| 新建轨迹 | high集合中confidence >= 0.25 | 保留；第一tick的初始化确认行为也保留 |
| 第一阶段 | score融合，门限0.8 | 保留 |
| 第二阶段 | 仅未匹配Tracked轨迹，纯IoU距离，门限0.5 | 恢复分支可达性；Lost仍不能低分恢复 |
| 未确认阶段 | score融合，门限0.7 | 保留；0.25–0.30附近的确认瓶颈留作后续研究 |
| Lost保留 | 30个更新tick | 保留；本轮不是统一真实dt的修复 |
| 计数 | A<0.4、B>0.6、连续3观察、最大间隔2秒 | 保留；空缺观察中断连续性 |

跟踪器low=0.1使用严格大于，解码保留采用大于等于。回归覆盖0.1、0.2、0.25及邻近值，不能把边界模糊写为统一闭区间。降低候选保留阈值属于下一轮单因素对照选项，R1不修改默认值。

评分v2的输入是完整通行事件，`time_s`为冻结规则下的通行完成源时间，`direction`为`A->B`或`B->A`；`event_id`建议提供，独立物理对应评价必须提供。`video_id`和`session_id`在每个事件记录中填写，两者不同则不能跨会话匹配。没有提供标识时视为单一共同范围。

匹配先约束同范围、同方向和时间容差，再最大化一对一匹配数，最后最小化总绝对时间误差。默认容差2秒继承历史开发口径，后续人工协议应事前冻结。纯Python动态规划按源时间和事件内容排序解决平局，使用独立穷举小样本验证优化目标。

每条输出保留原输入索引及事件ID。输入重排后索引随之改变，指标与有ID的语义配对保持一致；没有ID且内容完全相同的重复事件无法物理区分，仍按重复预测进入FP分母。存在多个时间候选时输出保守歧义标记，此标记不表示一定存在多个等价最优解，所有事件仍参与集合指标。

`physical_direction`只评价调用方提供的独立一对一对应，要求事件ID、复核标记、证据类型和证据说明；字段检查不会替代人工核实证据本身。没有对应证据时错误方向数输出null与UNDETERMINED状态，不能报告为0。即使方向集合完全正确，也不证明具体物理通行对应正确。

截断／不确定记录按预先约定单列并报告数量，不自动从JSON删除困难事件来改善分数。人工模板的events为空、状态pending；CLI拒绝pending或draft模板。旧评分器及历史成绩原样保存。
